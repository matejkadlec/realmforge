# content/

The single source of truth for all Realmforge game content. Everything derived from it (Java registrations,
models, textures, lang files, data, quests) is generated by `tools/` and must never be edited by hand.

| Directory | Model | One file per | Generates |
| --- | --- | --- | --- |
| `blocks/` | `BlockDef` (`tools/realmforge_tools/schema/block.py`) | block, `<id>.yaml` | registration with its block item (`GeneratedBlocks`; a `kind` other than `simple` through `world/BlockKinds`), blockstate, block and item models, opaque placeholder textures, loot table `data/realmforge/loot_table/blocks/<id>.json` (drops itself), vanilla mining tags (`minecraft:mineable/<tool>`, `minecraft:needs_<tier>_tool`), recipe `data/realmforge/recipe/<id>.json`, lang `block.realmforge.<id>`, QA expectations |
| `items/` | `ItemDef` (`tools/realmforge_tools/schema/item.py`) | item, `<id>.yaml` | registration (with its tooltip lines, from `use` and `flavor`), item model, lang, placeholder texture, the item tag `data/realmforge/tags/item/use/<use>.json` of each `use`, recipe `data/realmforge/recipe/<id>.json`, QA expectations |
| `curves/` | `CurveDef` (`tools/realmforge_tools/schema/curve.py`) | curve, `<id>.yaml` | `data/realmforge/realmforge/curve/<id>.json`, `ResourceKey` constant, lang (optional name), QA expectations |
| `stats/` | `StatDef` (`tools/realmforge_tools/schema/stat.py`) | attribute (a primary or secondary stat), `<id>.yaml` | registration in `GeneratedStats`, its name as the lang key `attribute.realmforge.<id>` (the attribute's description id), QA expectations |
| `stat_rules/` | `StatRuleDef` (`tools/realmforge_tools/schema/stat_rule.py`) | rule for one primary stat, `<id>.yaml` | `data/realmforge/realmforge/stat_rule/<id>.json`, QA expectations (the bonuses at sample stat values) |
| `spell_schools/` | `SpellSchoolDef` (`tools/realmforge_tools/schema/spell_school.py`) | spell school, `<id>.yaml` | `data/realmforge/realmforge/spell_school/<id>.json`, the damage type `data/realmforge/damage_type/<id>.json`, tag entries (`#minecraft:bypasses_cooldown` and `#minecraft:no_knockback`, magic schools also `#minecraft:bypasses_armor`), lang (name, death message), `ResourceKey` constants, QA expectations |
| `dimensions/` | `DimensionRulesDef` (`tools/realmforge_tools/schema/dimension_rules.py`) | rules of one dimension, `<id>.yaml` | `data/realmforge/realmforge/dimension_rules/<id>.json` (server only), QA expectations (the mob level rule's levels at sample positions) |
| `races/` | `RaceDef` (`tools/realmforge_tools/schema/character.py`) | playable race, `<id>.yaml` | `data/realmforge/realmforge/race/<id>.json`, lang (name, description), QA expectations (the bonuses) |
| `classes/` | `ClassDef` (`tools/realmforge_tools/schema/character.py`) | class, `<id>.yaml` | `data/realmforge/realmforge/class/<id>.json`, lang (name, description), QA expectations (resource, starting kit, the bonuses) |
| `texts/` | `TextGroupDef` (`tools/realmforge_tools/schema/text.py`) | group of texts, `<id>.yaml` | lang keys `<id>.realmforge.<name>`, constants in `GeneratedTexts` |
| `worldgen/<registry>/` | vanilla worldgen JSON (`tools/realmforge_tools/schema/worldgen.py` lists the registries) | entry, `<id>.json` | the same file, copied unchanged to `data/realmforge/<registry path>/` |
| `rooms/**/` | a structure template plus a `RoomDef` sidecar (`tools/realmforge_tools/schema/room.py`) | room, `<name>.nbt` + `<name>.yaml` | the template, normalized, at `data/realmforge/structure/rooms/<path>.nbt` (structure `realmforge:rooms/<path>`) |
| `dungeons/` | `DungeonTypeDef` (`tools/realmforge_tools/schema/dungeon.py`) | dungeon type, `<id>.yaml` | `data/realmforge/realmforge/dungeon_type/<id>.json` (server only) with its pool's rooms resolved (template, size, role, weight, connectors), the item tag `data/realmforge/tags/item/dungeon_key.json` of every type's `key`, lang (name), QA expectations |
| `kill_xp_multipliers/` | `KillXpMultiplierDef` (`tools/realmforge_tools/schema/kill_xp_multiplier.py`) | kill XP multiplier of one entity type, `<id>.yaml` | `data/realmforge/realmforge/kill_xp_multiplier/<id>.json` (server only), QA expectations (the multiplier at sample sizes) |
| `chapters/` | `ChapterDef` (`tools/realmforge_tools/schema/chapter.py`) | story chapter, `<id>.yaml` | `data/realmforge/realmforge/chapter/<id>.json`, its advancement `data/realmforge/advancement/chapter/<id>.json`, lang (name), QA expectations (the chapters, the level caps of sample sets of completed chapters, and leveling's XP numbers) |
| `spells/` | `SpellDef` (`tools/realmforge_tools/schema/spell.py`) | spell, `<id>.yaml` | `data/realmforge/realmforge/spell/<id>.json`, `ResourceKey` constants (`GeneratedSpells`), QA expectations |
| `realms/` | `RealmDef` (`tools/realmforge_tools/schema/realm.py`) | realm, `<id>.yaml` | `data/realmforge/realmforge/realm/<id>.json` (synced), its unlock advancement `data/realmforge/advancement/realm/<id>.json`, lang (name, subtitle, hint, flavour), QA expectations |

Rules:

- One YAML file per entry; the file name (without `.yaml`) must equal the entry's `id`.
- References to other content use full ids (`minecraft:ingredients`, `realmforge:test_item`); every one is
  validated against the ID universe (`tools/id_universe/`) plus our own content. Lists of ids must not repeat
  an entry (e.g. the same creative tab twice crashes the game).
- Player-facing texts are `LocalizedText` with one locale, `en_us`, which is required: Realmforge is English
  only (Matěj, 2026-10-13), so any other locale key (`cs_cz`, ...) is an error. In lore and texts the in-game
  world is always called **Realmforge**, and every text follows the [lore style guide](../docs/lore/style.md).
- **Community translations** need nothing from the pipeline: a translator ships a resource pack with
  `assets/realmforge/lang/<locale>.json`, keyed by the same translation keys as the generated `en_us.json`. A
  translation contributed to the mod is the same file under `mod/src/main/resources/`, which `rf gen` never
  touches.
- **Labels use Title Case** (Matěj, 2026-10-13), for readability: names (items, stats, spells, mobs, realms),
  key mapping names, setting names, screen, button and tab titles, guide chapter and section names, and short
  status messages: `Dark Vision On`, `Toggle Dark Vision`, `Character Sheet`. Every word starts with a capital
  except articles, conjunctions and prepositions of up to three letters (`a`, `an`, `the`, `and`, `but`, `or`,
  `of`, `in`, `on`, `at`, `to`, `for`, `by`) that are neither the first nor the last word: `Ring of the Deep`,
  `Dark Vision On`. Whole sentences (tooltip explanations, quest, lore and dialog text, a chat line that reads as
  a sentence) stay in sentence case.
- `texts/` holds player-facing texts that belong to no other type (key mapping names, messages). The group id
  is the key prefix (`key`, `message`, ...) and must not be another type's prefix (`item`, `curve`); Java
  names a text through its `GeneratedTexts` constant (`KEY_DARK_VISION`), never by typing the key. A group id may
  contain dots where the game prescribes a key format: `key.category.yaml` names key categories, which Options >
  Controls reads from `key.category.<namespace>.<path>` (constant `KEY_CATEGORY_MAIN`). `item_use.yaml` holds the
  green "Use:" tooltip line of each item use, named after the use; validation requires one for every use an item
  names.
- `items/` may give an item a `use`, what right-clicking it does, one item used up each time
  ([architecture 13](../docs/architecture.md#13-items-gear-and-loot)): `unlearn_stat_points` returns every spent
  stat point (the Scroll of Oblivion, RLM-196). The pipeline puts the item into the tag `realmforge:use/<use>`,
  which the game's code for that use reads. An optional `flavor` is a one-sentence flavor line under it in the tooltip, with no
  mechanics, at most 12 words ([lore style guide](../docs/lore/style.md)).
- `blocks/` may give a block a `kind`, what it does ([architecture 6.2](../docs/architecture.md#62-what-each-content-type-becomes)):
  `simple` (the default, a full block), `dungeon_portal` (a dungeon key opens it, lit while open; models `<id>` and
  `<id>_open`) or `dungeon_exit` (the way out of a dungeon, a plate one pixel high without collision; one block at
  most) ([15.5](../docs/architecture.md#155-instances)).
- `items/` and `blocks/` may give an entry a `recipe`: a shaped crafting recipe that makes it, its `pattern` (one to
  three rows of one to three characters, all the same width, a space for an empty slot), its `key` (each character
  of the pattern, and only those, to an item id), an optional `count` (1) and recipe book `category` (`misc`). It
  becomes vanilla's `minecraft:crafting_shaped` JSON.
- `dungeons/` names each type's `key`, the item that opens a dungeon portal to it (one type per key), and
  `open_minutes`, how long that portal stays open (1 to 240).
- Human units in YAML, game units in data: a field named `<name>_seconds` is written as `<name>_ticks`, one named
  `<name>_percent` as the fraction `<name>` ([architecture 6.3](../docs/architecture.md#63-conventions)).
- `stats/` defines our attributes ([architecture 8.1](../docs/architecture.md#81-the-attribute-set)). Every stat
  has a `name`, which the character sheet and item tooltips show. A stat counts points (`default`, `max`) or is a
  share (`default_percent`, `max_percent`, shown as a percentage); its minimum is 0, and a primary stat counts
  points. `stat_rules/` says what one primary stat gives, per point (with an optional cap, `max` or `max_percent`
  in the amount's unit) and at milestones
  ([8.3](../docs/architecture.md#83-derived-stats-and-milestones)). A rule reads a primary stat no other rule reads
  and writes only secondary stats and vanilla attributes (`minecraft:attack_damage`). An `add_value` amount on one
  of our stats takes its unit (`amount_percent` for a share, `amount` for points); on a vanilla attribute, whichever
  fits it (`minecraft:knockback_resistance` is a fraction, so `amount_percent: 5` adds 5 %). Multiplied operations
  always take `amount_percent`.
- `spell_schools/` defines the kinds of damage ([architecture 9.1](../docs/architecture.md#91-damage-pipeline)):
  `physical` (armor reduces it, it can be dodged) or `magic` (bypasses armor; spell power raises it). `power` and
  `resistance` name secondary stats that are shares (`fire_power`, `fire_resistance`), each serving one school.
  The death message names only the victim, `%1$s`: the game passes the killer only sometimes. `color` is the
  floating combat text's colour of the school's hits; the Physical school's colour is every hit's that is not magic
  (melee and ranged too), red on a crit.
- `dimensions/` holds the gameplay rules of a dimension, which `dimension` names (`minecraft:overworld`, or one of
  ours from `worldgen/dimension/`); at most one entry per dimension
  ([architecture 14.1](../docs/architecture.md#141-mob-levels)). Its optional `mob_levels` rule gives every hostile
  mob spawning there a level: `origin_level` at x 0, z 0, one more every `blocks_per_level` blocks of horizontal
  distance, one more every `depth.blocks_per_level` blocks below `depth.below_y`, then up to `jitter` levels either
  way at random (at most 1000), clamped to `min_level .. max_level`. What a level adds comes from the curves
  `mob_health` (a multiple of maximum health), `mob_damage` (a multiple of the damage of every hit the mob causes)
  and `mob_armor` (armor points). Its optional `access` lists what a player needs to enter the dimension, every one
  at once, refused on every way in (a portal, `/tp`, a warp; [architecture 15.1](../docs/architecture.md#151-dimensions)):
  `{type: realmforge:has_advancement, advancement: <id>}` (an advancement that exists, ours or vanilla's),
  `{type: realmforge:level_at_least, level: <n>}` or `{type: realmforge:chapter_completed, chapter: <chapter>}`.
- `blocks/` holds simple full blocks that drop themselves: `hardness` (stone 1.5, obsidian 50), `blast_resistance`
  (6 by default), the `tool` that mines it at full speed, `requires_tool` (drops nothing without that tool, as stone
  needs a pickaxe; needs a `tool`) with an optional `tool_tier` (`stone`, `iron`, `diamond`), its `sound` and
  `map_color` (vanilla's constants, lower case) and `creative_tabs`. Its block item takes its id, so no item in
  `items/` may share it. Undervault's four stones are the first (RLM-32).
- `realms/` holds the realms ([realm portal spec](../docs/design/realm-portal.md)): the realm's `dimension` (one of
  ours from `worldgen/dimension/`, one realm per dimension), its `name` without an article, its `subtitle` (the
  element), the `locked_hint` a refused player reads, a `flavour` line and the `icon` item of its unlock. The unlock is
  the advancement `realmforge:realm/<id>` (criterion `minecraft:impossible`: only the realm's quest or a command
  grants it), which the dimension's rules in `dimensions/` must name in their `access`. The realm's dimension type
  must link by a `coordinate_scale` above 1 and have a `minecraft:gameplay/bed_rule` that sets no spawn and does not
  explode. The portal's fields (sigil, colour, particle, sound, arrival) join with W2b.
- `races/` and `classes/` define who a player can be ([architecture 10.1](../docs/architecture.md#101-races-and-classes)).
  A race lists the classes it may take (each must exist, and every class must be open to some race) and gives
  `modifiers`; a class names its `resource` (`realmforge:mana` or `realmforge:rage`), gives `modifiers` and a
  `starting_kit` (items with a `count` of 1 to 64, given once when the character is created; every class's kit
  holds Bread ×32, Matěj, 2026-10-14, which validation checks). A modifier is the stat rules' shape (`attribute`,
  `operation`, `amount` or `amount_percent`, in the same units) and gives the same at every level: levels give stat
  points to spend instead (Matěj, 2026-10-15, RLM-196), so `per_level` is refused. A race's or class's `name` is a
  label (Title Case); its `description` is one or two sentences in the lore style guide's voice, which never assume
  the player's race or class.
- `chapters/` holds the story's chapters, which set the level cap
  ([architecture 10.2](../docs/architecture.md#102-leveling)). A chapter has a `name` (a label), an `order` (1, 2,
  3 without gaps), a `level_cap`, the cap while it is the player's current chapter (the first chapter's is a new
  player's cap), and a `completed_level_cap` above it, the cap once the player completes it; each chapter's
  `level_cap` equals the `completed_level_cap` of the one before it, so no level band is skipped (research PR-16).
  A player completes a chapter by earning its advancement `realmforge:chapter/<id>` (generated, granted only by
  the chapter's last quest or a command). A chapter's cap is its last level (Matěj, 2026-10-15): `chapter_1`
  (Overworld) 10 → 18, `chapter_2` (Undervault) 18 → 30; the later chapters' caps are in
  [architecture 10.2](../docs/architecture.md#102-leveling). XP stops at the cap: a player holds at most the XP
  of the cap's level, so completing a chapter raises the cap but brings no level by itself. Leveling also reads
  five curves, which validation requires: `xp_to_next_level` (the XP from a level to the next, at least 1; one
  point per level from the XP model, 1,500 at level 1 and 98,650 at 59), `kill_xp` (a kill's XP by the victim's
  level, `45 + 5 × level`), `kill_xp_below_player` and `kill_xp_above_player` (the share of it a kill gives, by how
  many levels the victim is below or above the player; the curve's `level` is that difference, and neither curve
  goes below 0), and `stat_points_per_level` (the primary stat points reaching a level gives, rounded half up, never
  below 0; level 1 gives none: 1 a level, Matěj, 2026-10-15, RLM-196).
- `kill_xp_multipliers/` gives the mobs of one entity type, named in `entity`, a kill XP `multiplier` (their rank: 1
  is a normal mob, 0 gives nothing, 10 a boss); a hostile mob without an entry gives 1. A slime or magma cube may
  give by size: `by_size` lists `{max_size, multiplier}` in increasing `max_size` order, the first one the mob's
  size does not exceed applies, and larger ones take `multiplier`. At most one entry per entity type
  ([architecture 10.2](../docs/architecture.md#102-leveling)).
- `spells/` holds the spells of players, mobs and bosses ([architecture 11](../docs/architecture.md#11-spells-and-status-effects)):
  the `school` whose damage they deal; what they `scales_with`, `spell_power` for a magic school and `attack_damage`
  for a physical one (off-class stats do nothing for a class's abilities, Matěj, 2026-10-15); their `targeting`
  (`{type: realmforge:self}`, or `realmforge:enemy`, `realmforge:ally`, `realmforge:ground_point` or
  `realmforge:direction` with a `range` of at most 128 blocks; an ally spell without a target takes the caster, a
  ground point without one the first block the caster looks at, a direction where it looks); `cast`: `{type: instant}`, `{type: cast_time, duration_seconds}`
  (the effects, the cost and the cooldown come when the cast completes) or `{type: channel, duration_seconds,
  interval_seconds}` (it pays and starts its cooldown when it begins, then runs its effects every interval; the
  duration is a whole number of intervals), the timed ones with `castable_while_moving` (moving cancels them by
  default; only the caster's own movement counts, a player's movement or jump key or a mob walking, never a push
  such as a melee hit's knockback, RLM-243) and `lock_on` (range and line of sight are not checked again before the effects); an optional `cost` (`resource` `realmforge:mana` or `realmforge:rage`, `amount` at level 1, `per_level`);
  `cooldown_seconds`; `global_cooldown_seconds` (1 by default, 0 for a spell off the global cooldown); `max_level`;
  the `crit` block (`can_crit`, `multiplier_percent` instead of 1 + the caster's crit damage, `bonus_chance_percent`
  added to the caster's crit chance; every spell can crit by default, heals too); `npc_only` for mob and boss
  spells; and the `effects`, in order: `realmforge:damage` (a hit of the school on an enemy) and `realmforge:heal`
  (on the caster or an ally), each with `amount` at level 1 and `per_level`, and `attack_damage_percent` (the share
  of the caster's attack damage added) on an attack damage spell, where its damage effects need one;
  `realmforge:apply_effect` (`effect`, a status effect id such as `minecraft:slowness`, `duration_seconds` up to 60,
  `amplifier`) and `realmforge:remove_effect` (`effect`) on any entity target; `realmforge:knockback` (`strength`,
  0.4 is a melee hit's) on an enemy, which also interrupts its cast; `realmforge:projectile` (`speed` in blocks per
  second, `size`, `lifetime_seconds`, and its own `effects` on the first enemy it hits) at an enemy, a ground point or
  along a direction; `realmforge:area` (`radius`, `duration_seconds`, `interval_seconds`, `affects: enemies` or
  `allies`, and its own `effects` on each of them inside at every interval) at the caster's feet, an enemy's or a
  ground point; `realmforge:teleport` (the caster to a ground point, or along a direction as far as its range and
  blocks allow); and `realmforge:dash` (`strength`, a burst of speed in blocks per tick toward an enemy, a ground
  point or along a direction). The effects of a projectile or an area must fit whom they reach: no heal on a
  projectile, no damage in an area for allies ([architecture 11.3](../docs/architecture.md#113-spell-entities)). A
  `per_level` needs a `max_level` above 1, on the effects of a projectile or an area too. Spells carry no name or description yet: those come with the spell bar and its
  tooltips (C3b, RLM-25). The `test_*` spells are engine tests (like `items/test_item`), not gameplay content.
- `worldgen/` is the one exception to YAML: Minecraft's own worldgen JSON (`dimension/`, `dimension_type/`,
  `biome/`, `noise_settings/`, ...), validated (location, id, JSON, dimension types, no clash with the core mod's
  own `realmforge:instances`) and copied byte for byte; the game decodes it when a world loads.
- `rooms/` is the second exception: dungeon rooms are structure templates (`.nbt`), each with a YAML sidecar of
  the same name ([architecture 15.4](../docs/architecture.md#154-rooms),
  [ADR 0028](../docs/decisions/0028-dungeon-rooms-generated-or-imported.md)). A room's id is its path below
  `rooms/` without the suffix (`third_party/stonevaults/hall_a`), in lowercase snake_case folders and names; the
  sidecar names the room `pools` the room joins (a dungeon type is built from one pool), its `tags` (slot types),
  its `weight` (how often the planner picks it among the rooms that fit, 1 to 150) and, for an imported room, its
  `source`. `uv run rf rooms import` writes both files ([tools/README](../tools/README.md#rooms)); nobody
  edits a template by hand. Validation checks the size (at most 48 blocks per axis), the template's data version
  (required, no newer than the game's), every block, block entity and entity id and every container's loot table
  against the ID universe, that jigsaws sit on the room's boundary, facing out, and that every jigsaw's pool is a
  vanilla template pool (`minecraft:empty` when it names none) or a room pool some sidecar lists. Imported rooms
  live in `rooms/third_party/<source>/` next to the source's `LICENSE` and `NOTICE` (and, for an LGPL-3.0 source,
  `COPYING`, the GPL-3.0 text), which validation requires and `rf gen` copies to the jar's
  `META-INF/third_party/<source>/`; an imported room elsewhere must be one we built ourselves, marked
  `source.ours: true` (`rf rooms import --ours`). The import rules of each source are in
  [art/rooms/](../art/rooms/README.md). A `review.yaml` in any folder records the room gallery's keep and reject
  decisions for the rooms below it: a kept room must exist, a rejected one may be dropped (the import then skips
  it).
- Room tags name the slots a room fills in a dungeon layout. `rf rooms import` drafts them for a new sidecar
  (`tools/realmforge_tools/rooms/slots.py`), and they are corrected by hand: one **role** (`entrance`, `hallway`,
  `combat`, `treasure`, `boss`, `stairs`), the **shape** its connectors give (`dead_end`, `straight`, `curved`,
  `t_junction`, `crossing`), and `vertical` when it connects up or down. So a straight hallway is
  `[hallway, straight]` and a treasure room at the end of a branch `[treasure, dead_end]`. Connectors of imported
  rooms are named `realmforge:door` on the sides and `realmforge:shaft` up and down. A room in the pool of a dungeon
  type must have exactly one role.
- A room marks spots with **data markers**: structure blocks in data mode whose metadata names `entrance` (where
  players arrive, one at most, only in an entrance room; without one they arrive at a free spot near the room's
  middle), `exit` (W4d), `mob` or `chest` (W6)
  ([architecture 15.3](../docs/architecture.md#153-generation-pure-first-then-minecraft)). The builder reads them
  and never places them, and validation refuses any other structure block. A room in the pool of a dungeon type
  keeps its fluids (water, lava, waterlogged blocks, kelp, seagrass) from reaching its sides and floor, through a
  floor hole or a wall gap too, where they would flow out of its box past what cleanup clears; only its connectors
  may let a fluid through, into the next room, and each only through its own face (not down out of a side
  connector in the floor layer, not sideways out of one on an edge).
- `room_specs/` holds the rooms the room generator builds (A4d,
  [architecture 15.4](../docs/architecture.md#154-rooms)): the `kind` (`entrance`; the hallways `corridor` with
  two opposite connectors, `curve` with two adjacent, `t_junction` with three, `crossing` with four and `dead_end`
  with one; `combat`; `treasure`; `arena`, the boss's room), the `theme` (`realmforge:<id>` of `room_themes/`), the
  `footprint` (`[x, z]`, 5 to 16 blocks, walls included), the `height` (5 to 16, floor and ceiling included), the
  `connectors` (the sides with a doorway), the `features` (`pillars`, `alcoves`, `pit`, `balcony`, `rubble`), and
  the `pools` and `weight` of its rooms. A feature that does not fit is refused (a pit needs 9 × 9 and a height of
  6, a balcony a height of 9 and a side without a doorway, alcoves such a side and 7 blocks, pillars 7 blocks).
  `seeds` are the candidates the gallery review kept: each is a room `generated/<spec>/seed_<n>` in the jar, with
  the tags of its kind and connectors. `rejected_seeds` are the ones it rejected. Both are written by
  `rf rooms review` on the candidates folder, as flow lists on one line (`seeds: [2, 7]`); see
  [tools/README](../tools/README.md#rooms). A generated room must let a player walk between its doorways with three
  blocks of headroom and leave no cell dark where a mob could spawn, which validation checks.
- `room_themes/` names, for each neutral role the room generator builds with (`floor`, `floor_variant`,
  `floor_border`, `wall_base`, `wall_body`, `wall_body_cracked`, `wall_body_mossy`, `wall_cornice`, `ceiling`,
  `pillar`, `stairs`, `slab`, `rubble`, `rubble_slab`, `wall_light`, `ceiling_light`), the block it is in this
  theme: a full solid block, a stairs block, a slab, a wall torch or a lantern as the role needs, each role its own
  block, so a theme swap (W4) can tell them apart. `stone_vault` is the one theme so far.
- `dungeons/` holds the kinds of dungeons ([architecture 15.2](../docs/architecture.md#152-dungeon-types)): a
  `name` (a label), the room `pool` the type is built from, and the `layout` the planner follows, each range
  written `[min, max]`: `main_path` (rooms between the entrance and the ending, 1 to 32), `branches` (side branches
  off the main path's rooms, 0 to 16), `branch_rooms` (rooms per branch, its dead end included, 1 to 8) and
  `ending` (`boss` or `treasure`, the role of the room that ends the main path). The planner closes every connector
  left over with a dead end, so a layout holds more rooms than these counts. Validation wants in the pool an
  entrance (role `entrance`, a connector), a room to pass through (role `hallway`, `combat` or `stairs`, two
  connectors; three when `branches` starts above 0), a room with the ending's role, and a dead end (one connector,
  role `hallway`, `combat`, `stairs` or `treasure`), and every connector of its rooms must meet one of the pool by the
  jigsaw rules (its `target` is the other's `name`; sides meet sides, up meets down). `rf gen` resolves the pool into
  the entry, so the game plans without loading a template. `test_dungeon` is test content (like `items/test_item`)
  that only `/qa dungeon plan`, `build` and `enter` use; W6 brings the real dungeon types.

  completion.
